# THE PLAY+ 고객지원 관리자 페이지 — 제품 요구사항 정의서(PRD)

- 문서 버전: 1.0
- 작성일: 2026-09-03
- 저장소: `theplayplus-admin`
- 상태: 현재 구현된 제품을 기준으로 한 정의서

## 1. 개요

**THE PLAY+ 고객지원 관리자 페이지**는 자사 게임과 서비스에 접수된 고객 문의를 한 화면에서 확인하고, 분류하고, 이메일로 답변하고, 처리 상태를 관리하는 사내 CS 도구다. 문의 접수 폼(`theplayplus-contact`)이 받아 저장한 문의를 처리하는 쪽을 담당하며, 두 저장소는 **같은 Supabase 프로젝트를 공유**한다.

관리자는 이 도구 안에서 문의 목록을 훑고, 한 건을 열어 사용자의 과거 문의 이력과 접수 정보를 확인하고, 답변을 작성해(필요하면 템플릿이나 AI 추천을 써서) `info@theplayplus.com` 계정으로 발송하고, 사용자의 회신까지 같은 화면에서 이어서 본다. 별도의 메일함을 열 필요가 없다.

### 이 문서의 위치

이 저장소에는 시점별 설계 문서 4건이 이미 있다. 각각은 그때 결정한 내용의 기록이고, 이 PRD는 그것들을 통합해 **"현재 이 제품이 무엇인가"**를 하나의 문서로 설명한다. 세부 구현 근거가 필요하면 아래 문서를 참조한다.

| 문서 | 다루는 범위 |
|---|---|
| `docs/superpowers/specs/2026-09-01-admin-panel-design.md` | 최초 설계 — 인증, 게임 관리, 문의 목록·상세, 답변 발송, 계정 이력, 서비스 문의 스펙 |
| `docs/superpowers/specs/2026-09-02-inquiry-detail-phase1-design.md` | 접수번호, 우선순위, 상세 화면 재구성 |

충돌이 있으면 이 PRD가 우선한다.

## 2. 배경과 문제

### 배경

`theplayplus-contact` 저장소가 `/contact` 문의 접수 폼을 만들면서 관리자 페이지는 범위 밖으로 두되 데이터 구조는 연동 가능하게 열어 뒀다. 이 저장소가 그 나머지 절반이다.

문의는 접수 폼에서 **anon 권한으로 `inquiries` 테이블에 직접 insert**된다. 이 저장소의 API를 거치지 않는다. 이 사실이 여러 설계 결정을 좌우한다 (9절 참조).

### 해결하려는 문제

관리자 도구가 없으면 문의는 DB에 쌓이기만 하고, 처리는 Supabase 대시보드를 직접 열어 행을 읽고 별도 메일 앱에서 답장하는 방식이 된다. 여기서 생기는 문제는 다음과 같다.

1. **처리 상태를 알 수 없다.** 어떤 문의가 답변됐고 어떤 게 방치 중인지 구분할 방법이 없다.
2. **문맥이 흩어진다.** 같은 사용자가 세 번째 보내는 문의인지, 지난번에 뭐라고 답했는지 확인하려면 매번 따로 찾아야 한다.
3. **답변이 기록되지 않는다.** 메일 앱에서 보낸 답변은 문의 데이터와 연결되지 않아 나중에 추적이 불가능하다.
4. **처리 이력이 없다.** 누가 언제 상태를 바꿨는지, 왜 그렇게 처리했는지 남지 않는다.
5. **반복 작업이 많다.** 비슷한 문의에 매번 같은 내용을 새로 타이핑한다.

## 3. 사용자와 이용 시나리오

### 사용자

| 사용자 | 설명 | 주 사용 기능 |
|---|---|---|
| **CS 담당자** (주 사용자) | 접수된 문의를 읽고 답변하는 실무자. 하루 대부분을 이 도구 안에서 보낸다. | 문의 목록, 문의 상세, 답변 발송, 템플릿, 메모 |
| **게임 운영 담당자** | 특정 게임의 문의 동향을 확인하고 필요 시 직접 처리한다. | 게임별 문의함, 상태 필터, 계정 이력 |
| **관리자(운영 총괄)** | 게임을 등록·삭제하고 전체 적체 상황을 본다. | 게임 관리, 게임 레일의 미처리 배지 |

**역할 구분은 시스템에 없다.** 로그인한 모든 관리자 계정은 동일한 권한을 갖는다 (4절 비목표 참조).

### 대표 시나리오

**시나리오 A — 아침 문의 처리 (CS 담당자)**

1. 로그인하면 좌측 게임 레일에 게임별 아이콘과 미처리(`접수`) 건수 배지가 보인다.
2. 배지 숫자가 가장 큰 게임을 클릭해 문의함에 들어간다.
3. 상태를 `접수`로 필터링하고 우선순위순으로 정렬한다. 긴급 건이 위로 올라온다.
4. 맨 위 문의를 연다. 상세 화면에서 접수번호, 접수 정보, 본문, 첨부파일, 그리고 우측에 이 계정의 과거 문의 이력이 함께 보인다.
5. 답변란 위 `AI 추천` 버튼을 눌러 초안을 받고, 문구를 다듬은 뒤 Cmd+Enter로 발송한다. 상태가 자동으로 `처리중`이 된다.
6. 헤더의 `다음` 버튼으로 같은 필터 안의 다음 문의로 넘어간다. 목록으로 돌아갈 필요가 없다.

**시나리오 B — 반복 문의 일괄 정리**

1. 문의함에서 검색어로 같은 성격의 문의를 모은다 (제목·접수번호·계정·본문 검색).
2. 체크박스로 여러 건을 고르고 상태를 한 번에 `완료`로 바꾼다. 건별로 변경 이력이 남는다.

**시나리오 C — 사용자 회신 확인**

1. 답변을 보낸 문의를 다시 연다.
2. `회신 확인` 버튼을 누르면 Gmail 스레드에서 사용자 회신을 가져와 대화 카드에 추가한다.
3. 같은 스레드로 후속 답변을 이어 보낸다. 사용자 쪽 메일함에서도 하나의 대화로 묶인다.

**시나리오 D — 재문의 사용자 응대**

1. 문의 상세 우측 계정 이력 패널에서 "이 계정 문의 4건 · 미처리 1건 · 같은 유형 2건" 요약을 본다.
2. 과거 문의 항목을 클릭해 지난 답변 내용을 확인한 뒤, 문맥에 맞는 답변을 작성한다.

## 4. 제품 목표와 비목표

### 목표

| # | 목표 | 판단 기준 |
|---|---|---|
| G1 | 문의 하나를 **처음부터 끝까지 이 도구 안에서** 처리한다 | 확인 → 답변 → 발송 → 상태 변경 → 회신 확인이 다른 도구 없이 가능하다 |
| G2 | 문의 처리 상태가 **항상 명확하다** | 모든 문의가 `접수`/`처리중`/`완료` 중 하나이고, 미처리 건수가 게임 레일에 보인다 |
| G3 | 답변에 필요한 **문맥이 한 화면에** 있다 | 본문, 접수 정보, 첨부, 대화 기록, 계정 이력, 내부 메모가 상세 화면에 함께 있다 |
| G4 | 반복 답변의 **작성 시간을 줄인다** | 템플릿 삽입과 AI 추천으로 초안을 얻는다 |
| G5 | 모든 처리에 **책임 소재가 남는다** | 상태·우선순위 변경, 답변 발송, 메모 추가가 행위자 이메일과 함께 기록된다 |
| G6 | 게임이 늘어나도 **구조 변경 없이 확장된다** | 게임 추가 시 문의 카테고리가 자동 시드되고 문의함이 바로 열린다 |

### 비목표 (의도적으로 만들지 않은 것)

| 항목 | 제외 이유 |
|---|---|
| **관리자별 권한 제어** | 사내 소수 인원이 쓰는 도구다. 게임별 담당자(`owner_name`)는 표시용 텍스트일 뿐 접근을 제한하지 않는다. 인원이 늘고 위임이 필요해지면 그때 설계한다. |
| **다국어 관리자 UI** | 운영자는 전원 한국어 사용자다. 사용자에게 나가는 메일과 문의 폼만 다국어를 지원하면 된다. |
| **담당자 배정** | 관리자 계정 목록의 출처(Supabase Auth 조회 vs 별도 `admins` 테이블)를 정하는 일이 딸려 온다. 지금 결정을 서두를 이유가 없다. |
| **보상 지급 패널** | 이 저장소에 게임 내 재화를 지급할 수단이 없다. GM 툴 연동이 생기면 그때. |
| **이벤트 참여 이력** | 데이터 소스가 아직 없다. `AccountHistoryPanel`에 확장 지점만 주석으로 남겼다. |
| **메모 수정·삭제** | 감사 성격의 기록이라 추가만 가능하게 둔다. |
| **템플릿 수정** | 추가와 삭제만 지원한다. 고칠 일이 있으면 지우고 다시 만든다. 편집 폼을 만들 만큼 자주 바뀌지 않는다. |
| **AI 추천 후보 여러 개 / 자동 추천** | 토큰 비용과 대기 시간이 배로 늘어난다. 하나만 받고, 마음에 안 들면 다시 누른다. 화면을 열 때마다 API를 호출하지 않는다. |
| **메인 사이트 저장소로의 자동 배포** | 이 저장소의 코드는 사람이 직접 메인 사이트 저장소로 복사해 통합한다. |

## 5. 기능 요구사항

각 기능의 요구사항(FR)과 수용 기준을 정리한다. 별도 표기가 없으면 **모두 구현 완료** 상태다.

### 5.1 인증

| ID | 요구사항 |
|---|---|
| FR-1.1 | Supabase Auth 이메일+비밀번호로 로그인한다. 관리자 계정은 여러 개일 수 있고 역할 구분은 없다. |
| FR-1.2 | 미인증 상태로 관리자 화면에 접근하면 `/login`으로 리다이렉트한다. 미들웨어가 처리한다. |
| FR-1.3 | 이미 로그인한 상태로 `/login`에 접근하면 관리자 화면으로 돌려보낸다. |
| FR-1.4 | 모든 API 라우트는 요청마다 세션을 검증하고, 없으면 401을 반환한다. |
| FR-1.5 | 게임 레일 하단에서 로그아웃한다. |

**수용 기준**: 리다이렉트 규칙은 `lib/auth-routing.ts`의 순수 함수 `resolveAdminAuthRedirect()`로 분리되어 단위 테스트로 검증된다.

### 5.2 게임 관리

| ID | 요구사항 |
|---|---|
| FR-2.1 | 게임을 추가한다. 이름(필수, 1~100자), 상태(`서비스중`/`종료`, 필수), 담당자명(선택), 로고 이미지(선택). |
| FR-2.2 | 게임 생성 시 기본 문의 카테고리 템플릿(`inquiry_groups`/`inquiry_types`)을 그 게임용으로 자동 복사한다. |
| FR-2.3 | 로고 업로드가 실패해도 게임 생성은 성공시키고 경고만 표시한다. 반대로 **카테고리 시드가 실패하면 게임 생성을 롤백한다** — 카테고리 없는 게임은 문의를 받을 수 없기 때문이다. |
| FR-2.4 | 좌측 게임 레일에 등록된 게임을 로고(없으면 이름 첫 글자)로 나열하고, 클릭하면 그 게임의 문의함으로 이동한다. |
| FR-2.5 | 게임 레일의 각 아이콘에 미처리(`접수`) 문의 건수를 배지로 표시한다. 0건이면 배지를 그리지 않는다. |
| FR-2.6 | 게임을 삭제한다. 딸린 문의·첨부파일·카테고리를 함께 정리하며, 삭제 전 문의 건수를 보여준다. Storage 파일 정리는 best-effort로 처리해 삭제 자체를 막지 않는다. |
| FR-2.7 | 등록된 게임이 하나도 없으면 안내 화면을 보여주고, 있으면 첫 게임의 문의함으로 리다이렉트한다. |

**한계**: 게임 정보 **수정** 기능은 없다 (생성·삭제만). 게임별 카테고리 편집 UI도 없다 — 시드된 카테고리를 바꾸려면 Supabase에서 직접 수정해야 한다 (12절 참조).

### 5.3 문의 목록 (문의함)

| ID | 요구사항 |
|---|---|
| FR-3.1 | 선택한 게임의 문의를 목록으로 보여준다. 한 페이지 **50건**, 페이지 이동 지원. |
| FR-3.2 | 필터: 문의 종류(그룹), 문의 유형, 처리 상태. |
| FR-3.3 | 정렬: 최신순(기본) / 오래된순 / 우선순위순. 우선순위순은 `긴급 > 높음 > 보통 > 낮음`, 동순위는 최신순. |
| FR-3.4 | 검색: 제목, 접수번호, 게임 계정, 본문을 대상으로 부분 일치 검색. |
| FR-3.5 | **필터·정렬·검색·페이지 상태는 전부 URL 쿼리에 담긴다.** 링크를 공유해도, 상세에 들어갔다 뒤로 와도 같은 화면이 나온다. 기본값과 같은 항목은 URL에서 생략한다. |
| FR-3.6 | 잘못된 쿼리 값(존재하지 않는 상태, 음수 페이지 등)은 오류 없이 조용히 기본값으로 떨어뜨린다. URL은 사람이 손으로도 고치기 때문이다. |
| FR-3.7 | 체크박스로 여러 건을 선택해 상태를 일괄 변경한다. 한 번에 최대 100건. 이미 그 상태인 건은 건너뛴다. |
| FR-3.8 | 일괄 변경도 건별로 변경 이력을 남긴다. |
| FR-3.9 | 목록의 각 행은 접수번호, 제목, 상태, 우선순위, 경과 시간을 보여준다. |

**수용 기준**: 필터·정렬·검색·페이징은 **모두 DB에서 처리한다.** 문의가 수만 건 쌓여도 목록이 느려지지 않아야 하므로 전체를 가져와 클라이언트에서 거르지 않는다.

**보안**: 검색어의 쉼표·괄호·와일드카드(`%`, `_`)는 제거한다. PostgREST의 `or()` 필터 문법이 깨지는 것을 막고, 사용자가 의도하지 않은 와일드카드 매칭을 방지한다.

### 5.4 문의 상세

한 화면을 헤더 / 본문 열 / 사이드 열로 구성한다.

| ID | 요구사항 |
|---|---|
| FR-4.1 | **헤더** — 접수번호, 제목, 종류·유형 라벨, 상태 배지, 우선순위, 경과 시간, `완료로 표시` 버튼. |
| FR-4.2 | **본문 카드** — 문의 원문과 첨부파일. 첨부는 1시간 유효 서명 URL로 제공한다 (버킷은 비공개). |
| FR-4.3 | **대화 카드** — 관리자 답변(outbound)과 사용자 회신(inbound)을 시간순으로 보여준다. |
| FR-4.4 | **접수 정보 카드** — 고정 필드(계정, 회사명, 회신 이메일, 접수일)와 함께 `meta` jsonb를 자동 렌더한다. 접수 폼이 새 필드를 보내기 시작하면 이 저장소의 코드 수정 없이 화면에 나타난다. |
| FR-4.5 | **내부 메모** — 운영자 전용 메모를 추가한다. 사용자에게 절대 노출되지 않는다. 작성자 이메일과 시각이 함께 남는다. |
| FR-4.6 | **변경 이력** — 상태 변경, 우선순위 변경, 답변 발송, 메모 추가를 행위자와 함께 시간 역순으로 보여준다. 목록 맨 아래의 "접수" 항목은 저장하지 않고 `created_at`으로 화면에서 합성한다. |
| FR-4.7 | **계정 이력 패널** — 5.6 참조. |
| FR-4.8 | 상태와 우선순위를 셀렉트로 직접 변경한다. |
| FR-4.9 | **이전/다음 이동** — 목록에서 들고 온 필터·정렬 안에서 앞뒤 문의로 이동한다. 목록으로 돌아가지 않고 연속 처리할 수 있다. |
| FR-4.10 | `← 목록` 링크는 들어올 때의 필터·정렬·페이지를 그대로 복원한다. |

**경과 시간 표기**: 분 → 시간 → 일로 자동 전환한다 (목록·상세 공통).

### `inquiries` 주요 컬럼

| 컬럼 | 설명 |
|---|---|
| `inquiry_no` | 접수번호 `R-YYYYMMDD-NNNN`. DB 트리거가 부여한다. |
| `game_id` | 게임 참조. **nullable** — 게임과 무관한 서비스 문의가 있을 수 있다. |
| `group_key` / `type_key` | 카테고리 키. FK가 아닌 문자열이다. |
| `game_account` | 게임 계정. 계정 이력 매칭의 키. |
| `status` | `new` / `in_progress` / `resolved` |
| `priority` | `urgent` / `high` / `normal` / `low` (기본 `normal`) |
| `priority_rank` | 정렬용 생성 컬럼 (urgent=0 … low=3). `priority`를 그대로 정렬하면 알파벳순이 되어 쓸모없다. |
| `meta` | jsonb. 접수 폼이 보내는 부가 정보를 담고, 상세 화면이 자동 렌더한다. |
| `draft_reply` | 작성 중인 답변 초안 |
| `reply_content` / `replied_at` | 마지막 답변과 그 시각 |
| `gmail_thread_id` | Gmail 스레드 연결 |

### 접수번호 채번 규칙

`R-` + KST 기준 날짜(`YYYYMMDD`) + `-` + 그날의 4자리 일련번호. 예: `R-20260903-0007`.

- **DB의 `before insert` 트리거가 부여한다.** 접수 폼이 이 저장소의 API를 거치지 않고 직접 insert하므로, 앱 레이어에서 채번하면 그 경로로 들어온 문의에 번호가 빠진다.
- 날짜별 시퀀스 테이블에 `on conflict do update`로 증가시킨다. 행 잠금이 동시 접수 시의 번호 중복을 원천 차단한다. `count(*) + 1` 방식은 이 이유로 탈락했다.
- 트리거는 `security definer`로 실행하고 `search_path`를 비운다. anon 권한으로 들어오는 insert가 RLS에 막히면 문의 접수 자체가 실패하기 때문이다.
- 마이그레이션은 기존 문의에 소급 부여하며, 정렬 기준(`created_at`, 동률이면 `id`)을 못 박아 재실행해도 같은 결과가 나온다.

### RLS 정책

| 대상 | anon (접수 폼) | 이 저장소 |
|---|---|---|
| `games` | 서비스중(`active`) 게임만 select | service-role로 전체 접근 |
| `inquiry_groups` / `inquiry_types` | select만 | service-role로 전체 접근 |
| `inquiries` / `inquiry_attachments` | insert만 | service-role로 전체 접근 |
| `inquiry_number_seq` | RLS 켜고 정책 없음 → 전면 차단 | 트리거가 `security definer`로 우회 |
| `inquiry_notes` / `inquiry_events` / `reply_templates` / `inquiry_messages` | RLS 켜고 정책 없음 → 전면 차단 | service-role로만 접근 |

관리자 앱은 service-role 클라이언트를 쓰므로 RLS를 우회한다. 접근 통제는 미들웨어와 API 라우트의 세션 검증이 담당한다.

### Storage 버킷

| 버킷 | 공개 여부 | 용도 |
|---|---|---|
| `game-logos` | 공개 읽기 | 게임 로고 |
| `inquiry-attachments` | 비공개 | 문의 첨부. 관리자에게만 1시간 서명 URL로 제공 |

로고 파일 키에는 원본 파일명을 쓰지 않는다 — Supabase Storage는 비 ASCII 키를 거부하는데, 한글 로고 파일명이 정확히 그 경우다.

## 7. 외부 연동

### Gmail API (`googleapis`)

- `info@theplayplus.com` Google Workspace 계정으로 발송한다.
- 필요한 스코프: 발송(`gmail.send` 상당)과 회신 동기화를 위한 `gmail.readonly`.
- 메일은 RFC 2822 형식으로 직접 조립해 base64url로 인코딩한다. `Message-ID`도 직접 생성한다 — Gmail이 붙여주는 값을 다시 읽으려면 발송 후 조회를 한 번 더 해야 하는데, 직접 넣으면 Gmail이 그대로 보존한다.
- refresh token은 **최초 1회 계정 소유자가 OAuth 동의 화면에서 직접 발급**해야 한다. 코드로 자동화되지 않는 수동 준비 단계이며 `scripts/get-gmail-refresh-token.js`가 이를 돕는다.

### Gemini API (`@google/genai`)

- 답변 추천에만 쓴다. 모델은 `GEMINI_MODEL` 환경변수로 교체 가능하다 (기본 `gemini-3.5-flash-lite`).
- 구버전 SDK `@google/generative-ai`는 쓰지 않는다.

### Supabase

- Auth: 관리자 로그인 (이메일+비밀번호)
- Postgres: 6절의 데이터 모델
- Storage: 로고·첨부

### 환경변수

```
NEXT_PUBLIC_SUPABASE_URL / NEXT_PUBLIC_SUPABASE_ANON_KEY   # 브라우저·미들웨어 (Auth)
SUPABASE_URL / SUPABASE_SERVICE_ROLE_KEY                    # 서버 (RLS 우회)
GMAIL_CLIENT_ID / GMAIL_CLIENT_SECRET / GMAIL_REFRESH_TOKEN / GMAIL_SENDER
GEMINI_API_KEY / GEMINI_MODEL
```

**이 값들은 어떤 문서나 커밋에도 평문으로 남기지 않는다.** `.env`로만 관리하며, 저장소에는 빈 `.env.example`만 둔다.

## 8. 비기능 요구사항

| 영역 | 요구사항 |
|---|---|
| **성능** | 문의 목록의 필터·정렬·검색·페이징을 전부 DB에서 처리한다. 한 페이지 50건. 상세의 이전/다음 이동용 id 목록은 최대 1000건으로 자른다. |
| **렌더링** | 관리자 화면은 `dynamic = "force-dynamic"`으로 매 요청 서버 렌더한다. 문의 상태는 실시간성이 중요해 캐시하지 않는다. |
| **보안** | 시크릿은 `.env`로만 관리한다. service-role 키는 서버에서만 쓴다. 첨부파일은 비공개 버킷 + 만료되는 서명 URL로만 접근한다. 검색어는 필터 문법을 깨는 문자를 제거한다. 트리거의 `search_path`를 비워 검색 경로 하이재킹을 막는다. |
| **감사성** | 상태·우선순위 변경, 답변 발송, 메모 추가는 행위자 이메일과 함께 기록된다. 계정이 삭제돼도 기록이 남도록 이메일을 비정규화해 저장하고 `auth.users`에 FK를 걸지 않는다. |
| **입력 검증** | 모든 API는 zod로 요청을 검증한다. 클라이언트 검증은 편의일 뿐이고 서버가 다시 검증한다. |
| **접근성** | 상태 배지에 `aria-label`, 게임 레일에 `aria-current`/`aria-label`, 미처리 배지에 건수 라벨을 붙인다. |
| **품질** | Vitest + React Testing Library. 현재 **테스트 파일 50개, 테스트 343건 전부 통과** (2026-09-03 기준). API 라우트, 순수 함수, 컴포넌트를 각각 다룬다. |
| **UI 언어** | 한국어 전용. |
| **런타임** | Node.js 20 이상. |

## 9. 설계 원칙 (확정된 결정)

이 제품의 코드를 고칠 때 지켜야 하는 규칙이다. 각 항목은 이미 내려진 결정이며 근거와 함께 남긴다.

### 9.1 부가 작업의 실패가 핵심 데이터 저장을 막지 않는다

로고 업로드, 이메일 발송, 이력 적재처럼 실패해도 되는 작업이 실패했다고 게임이나 문의 저장을 롤백하지 않는다. 경고를 표시하고 재시도할 수 있게 한다.

- 상태 변경이 성공한 뒤 이벤트 insert가 실패하면 서버 로그에 경고만 남기고 API는 성공을 반환한다. 이력 한 줄 때문에 상태 변경이 되돌아가는 쪽이 나쁘다.
- 답변 발송도 같다. **메일이 이미 나갔으면 기록 실패로 되돌릴 수 없다.** 대신 경고를 내려 관리자가 스레드에 빠진 답변이 있음을 알게 한다.
- 예외: 카테고리 시드 실패는 게임 생성을 롤백한다. 카테고리 없는 게임은 문의를 받을 수 없어 반쪽짜리 데이터가 되기 때문이다.

### 9.2 접수 폼이 anon으로 직접 insert한다는 전제

`theplayplus-contact`의 접수 폼은 이 저장소의 API를 거치지 않는다. 따라서 **모든 문의에 반드시 적용돼야 하는 규칙은 DB에 있어야 한다.** 접수번호 채번을 트리거로 구현한 이유이자, 그 트리거를 `security definer`로 실행하는 이유다.

같은 이유로 "접수" 이벤트는 `inquiry_events`에 쌓지 않는다. 그러려면 트리거를 하나 더 만들고 RLS와 `security definer`를 또 다뤄야 하는데, `inquiries.created_at`이 이미 그 정보를 갖고 있으므로 화면에서 합성한다.

### 9.3 카테고리는 하드코딩하지 않는다

문의 종류·유형은 DB(`inquiry_groups`/`inquiry_types`)에서 게임별로 관리한다. `lib/categories.ts`의 `DEFAULT_CATEGORY_TEMPLATE`은 게임 생성 시 복사되는 **초기 시드**일 뿐이고, 화면은 항상 DB를 읽는다.

시드 데이터는 `label_ko`/`label_zh`/`label_en`을 모두 채운다. 이후 관리자가 추가하는 카테고리는 한국어만 입력하고, 문의 폼 쪽에서 비어 있으면 `label_ko`로 대체 표시한다.

### 9.4 행위자 정보를 비정규화한다

`inquiry_notes.author_email`, `inquiry_events.actor_email`에 이메일 문자열을 그대로 저장한다. `auth.users`는 Supabase가 관리하는 보호된 스키마라 매번 조인하는 것이 번거롭고 느리며, 감사 기록은 계정이 삭제된 뒤에도 남아야 하기 때문이다. `author_id`/`actor_id`도 함께 남기되 FK 제약은 걸지 않는다.

### 9.5 순수 함수로 분리해 테스트 가능하게 만든다

외부 API나 DB를 때려야만 테스트할 수 있는 로직은 아무도 고치지 못한다. 핵심 로직은 순수 함수로 떼어낸다.

- `resolveAdminAuthRedirect()` — 인증 리다이렉트 규칙
- `parseInquiryListQuery()` / `toInquiryListSearch()` — URL 쿼리 파싱·직렬화
- `buildSuggestPrompt()` — AI 프롬프트 조립
- `encodeRfc2822Message()` / `stripQuotedReply()` / `extractPlainText()` — 메일 조립·파싱
- `describeEvent()` — 이력 문구 생성
- `sanitizeSearch()` — 검색어 정제

### 9.6 URL이 화면 상태의 원본이다

목록의 필터·정렬·검색·페이지는 컴포넌트 state가 아니라 URL 쿼리가 원본이다. 링크 공유, 뒤로 가기, 상세에서 목록 복귀가 모두 같은 메커니즘으로 동작한다.

### 9.7 파일이 커지면 쪼갠다

`lib/inquiries.ts`가 커졌다는 이유로 추천 기능이 쓰는 조회를 `lib/replies.ts`로 분리했다. 한 파일 한 목적을 유지한다.

## 10. 제약과 의존성

| # | 제약 | 영향 |
|---|---|---|
| C1 | **Supabase 프로젝트를 `theplayplus-contact`와 공유한다** | 스키마 변경이 접수 폼에 즉시 영향을 준다. 마이그레이션은 이 저장소가 소유하되 파괴적 변경 전에 접수 폼 쪽 사용처를 확인해야 한다. |
| C2 | **마이그레이션이 재실행 가능해야 한다** | 두 저장소가 각자 마이그레이션을 돌릴 수 있어 `if not exists`, 정책 `drop` 후 `create` 패턴을 쓴다. 정책 이름 충돌로 트랜잭션이 중단되면 RLS 활성화까지 조용히 되돌아간다. |
| C3 | **메인 사이트 저장소로 사람이 직접 복사해 통합한다** | 자동 배포 파이프라인이 없다. 스택(Next.js App Router + Tailwind)을 메인 사이트와 동일하게 유지해야 복사가 가능하다. |
| C4 | **Gmail refresh token은 수동 발급이다** | 계정 소유자가 OAuth 동의를 거쳐야 하고, 토큰이 만료되면 발송이 중단된다. 실패 시 답변은 폼에 유지되고 상태는 바뀌지 않는다. |
| C5 | **Gmail API 할당량과 발송 한도** | 대량 발송 도구가 아니다. 하루 처리량이 크게 늘면 할당량 검토가 필요하다. |
| C6 | **접수 폼의 `meta` 필드 스키마가 이 저장소와 분리돼 있다** | 접수 폼이 무엇을 보낼지 이 저장소가 강제하지 않는다. 그래서 `meta`를 자동 렌더해 코드 수정 없이 새 필드가 화면에 나타나게 한다. |
| C7 | **디자인은 기존 사이트 테마를 따른다** | `#0a0a0a` 배경, `#EA581F` 포인트 컬러. |

## 11. 성공 지표

이 도구가 잘 작동하는지 판단하는 기준이다. 현재 계측 기능은 구현되어 있지 않으며, 아래 수치는 `inquiry_events`와 `inquiries` 데이터로 산출할 수 있다.

| 지표 | 정의 | 목표 |
|---|---|---|
| **첫 응답 시간** | `created_at` → 첫 `reply_sent` 이벤트까지의 시간 (중앙값) | [확인 필요 — 팀 SLA 미정] |
| **미처리 적체** | 상태가 `접수`인 문의 건수 (게임 레일 배지로 상시 노출) | 영업일 마감 기준 0에 수렴 |
| **미처리 최장 대기** | 상태가 `접수`인 문의 중 가장 오래된 건의 경과 시간 | [확인 필요] |
| **재문의율** | 같은 `game_account`가 30일 내 다시 문의한 비율 | 하락 추세 |
| **템플릿·AI 활용률** | 답변 중 템플릿 삽입 또는 AI 추천을 거친 비율 | 계측 미구현 — 필요 시 이벤트 추가 |
| **답변 1건 처리 시간** | 상세 화면 진입 → 발송까지 | 계측 미구현 |
| **회신 동기화 누락** | `gmail_thread_id`가 있는데 inbound 메시지를 한 번도 가져오지 않은 문의 비율 | 수동 동기화의 한계를 판단하는 근거 (12절 참조) |

**현재 운영 규모**(월 문의량, CS 담당 인원 등)는 이 저장소의 코드로 확인할 수 없다 — [확인 필요].
